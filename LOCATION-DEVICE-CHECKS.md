# Attendance monitoring: implementation and device acceptance

The app uses authenticated REST and `policy.tracking` from MOBILE-LOCATION.md. A session-bound Riverpod monitor follows the exact open ID from `/attendance/me`, for the current server workDate. It starts on launch/sign-in and successful attendance refresh, reconciles on resume, and stops on confirmed manual/automatic checkout, logout, account change or 401. Logout clears local access before remote revocation. Requests are cancelled and old capture/response generations are discarded on stop; shared-client request revisions prevent an old report using a new account's token.

Geolocator's continuous stream uses Android's location foreground service, zero movement filter and the policy interval, with a persistent notification/wake lock; iOS enables background updates and disables automatic pausing. A periodic fresh capture also aims for stationary reporting. Uploads are serialized, busy stream events are dropped, and capture timestamps come from Position.timestamp. No coordinate queue, last-known-position fallback, off-duty history, distance/departure calculation or local checkout exists. Invalid, old, duplicate and future fixes become `{available:false}`. Positive poor accuracy is reported unchanged for server classification. Network failure is visible; no fix is replayed on recovery. Accepted updates and 404/409 trigger attendance reconciliation. Manual GPS/photo capture and the one-interval workday rule remain unchanged.

The app-wide English/Arabic banner explains tracking before its permission action, shows server deadlines/countdowns, distinguishes unavailable location from connection errors, and links to app/location settings. A return window posts one local warning; cancellation, checkout and sign-out remove it. Notification denial retains the visible warning. At expiry the app reads attendance immediately and every ten seconds until the server clears the deadline. These reads do not close attendance. Attendance payloads/error bodies are excluded from Dio logging.

## Platform scope and limits

This checkout contains Android and iOS runners only. Desktop/web capture is unsupported. Existing Flutter minimum SDK values remain; iOS is configured for 13+. Android permissions include precise/coarse/background location, location foreground service, wake lock and notifications. Notification icons are retained for resource shrinking. Android uses Java 17, AGP 8.11.1 and desugaring. iOS includes Always usage text, the location background mode, a notification delegate, and a CocoaPods file enabling permission_handler's location permission group without Geolocator's Always bypass flag. Run pod install and verify signing/capabilities on a Mac.

Background delivery is best effort. The service is attached to the running Flutter engine; it does not restart a terminated/force-stopped app or survive a reboot by itself. Android battery restrictions/OEM task killers and iOS suspension can interrupt reporting; stationary iOS delivery particularly needs a pilot. No persistent background engine or offline replay is added. Missing reports become unavailable through the server's stale-evidence rules, leaving attendance open. Notification permission, Focus/Do Not Disturb and OS policy can suppress alerts. Restart clears an old local warning and restores only the deadline returned by the server. Device clock changes can distort the rendered countdown; the server still owns expiry and rejects bad capture times.

Configuration references: [Geolocator platform setup](https://pub.dev/packages/geolocator#usage) and [local notifications platform setup](https://pub.dev/packages/flutter_local_notifications#android-setup). The installed package source was also checked for the actual settings and API signatures.

## Required real-device pilot

Use isolated employee accounts and a reachable HTTPS backend. Record phone/OS/app versions, policy response, times observed by HR, permission states, battery settings and pass/fail evidence. Keep coordinates, bearer tokens and employee data out of console/crash logs. Do not use production attendance for destructive tests.

1. **On/off duty and stationary:** Before check-in, verify no location service or requests. Check in within the separate 50-metre manual boundary with a photo. Enable explained permissions. Leave the phone stationary inside for at least ten minutes, foreground then background/locked. Compare fresh report times and exact record ID with HR; target 30 seconds, document actual gaps. Check out; confirm the stream, foreground service and warnings stop. Verify an older unresolved interval uses the forgotten-checkout flow and is not monitored as a current on-duty interval.
2. **Departure/return:** One reliable outside reading must not start a timer. Two readings received at least policy confirmationSeconds apart start the server's five-minute deadline. Compare UI/notification times with HR. Ongoing outside readings must preserve the deadline. Return reliably inside before expiry; confirm deadline and local warning clear. Repeat with poor accuracy and uncertain boundary overlap; server state must be unavailable, deadline null, attendance still open.
3. **Automatic checkout:** Remain reliably outside and report fresh fixes through expiry. Wait for the worker/read-back. Verify exactly one checkout at the server deadline and one audit, no photo/deduction, stopped tracking, and no second check-in that workday. Confirm manual checkout and HR correction also stop reporting.
4. **Permission/service loss:** Test deny, permanent denial, approximate/reduced accuracy, Always downgrade, GPS disabled, and settings recovery while locked and unlocked. Confirm `{available:false}` contains no other fields when connected, unavailable guidance and an open interval. Any countdown must cancel on the server. Recovery requires new confirmation and a full window, never the previous deadline. Verify notification denial retains the app warning and settings guidance.
5. **Network loss:** Disable Wi-Fi/data during a return window and through expiry. Verify a connection problem, no queued/replayed fixes, server stale-unavailable cancellation and no checkout/deduction. Restore access; verify new capture timestamps, reconciliation and a new confirmation window. Test DNS errors, timeouts, proxy failures and backend restart.
6. **Lifecycle/termination:** Repeat with screen locked, app switch, low-power/battery restriction, OEM task removal, swipe termination, force stop, reboot and low-memory process death. Record delivery gaps honestly. On relaunch/resume, GET attendance/policy before restarting reports. Verify valid deadlines restore; stale periods cancel on the server. Terminated-app tracking is not guaranteed or implemented.
7. **Identity/security:** Logout while capture/upload is pending, including offline logout. Switch between two employees; old results must not update the new UI or post coordinates with its credentials. Revoke the session and verify 401 stops tracking and warns no longer. Exercise closed/wrong-owned IDs and 409 timestamp rejection against the isolated backend; reconcile rather than retrying the same fix. Inspect logs for absence of coordinates and tokens.
8. **Clock and UI:** Change device timezone/time, test Arabic/RTL, dark mode, small screens and large text. Server saved timezone/deadline remains authoritative. At zero, show checking state until read-back; never fabricate checkout. Verify return warnings on Android 13+ notification permission, Android 14+ location-service restrictions, and supported iOS versions/Focus modes.

## Workspace verification

Run `flutter pub get`, localization generation, `flutter analyze`, `flutter test`, and Android/iOS builds on appropriate hosts. Focused monitor tests are in `test/attendance_location_test.dart`; they cover payloads, policy separation, freshness, stationary timer capture, ordering, off-duty behavior, permission/network loss, server deadlines, 409/401, checkout and disposed-account responses. These are host tests with mocked location/REST; they do not verify phone operation or the live backend worker/audit. The referenced hr-backend checkout is absent here, so backend/device acceptance remains a separate pilot.

Verified in this Windows workspace on 2026-10-12: dependency resolution and localization generation passed; Flutter analysis reported no issues; the full Flutter suite passed 177 tests with 6 opt-in backend/benchmark cases skipped. Platform XML/plist parsing passed. Added widget coverage checks English/light and Arabic/dark layouts at 320×640 with 1.8× text, deadline read-back and warning removal. A mocked native-notification check verifies serialized show/cancel ordering. Additional checks cover permission loss during an upload and confirmed attendance writes with failed read-back. Android debug build was attempted twice (including IPv4 preference) but Gradle failed before compilation with `java.io.IOException: Unable to establish loopback connection`. No iOS build was possible on Windows. Flutter listed only Windows/Chrome/Edge, with no connected phone; no real-device or live-worker acceptance is claimed.
