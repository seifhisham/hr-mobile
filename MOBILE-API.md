# Mobile app API and implementation guide

Verified against the backend source on 2026-10-06. This is the shared Flutter integration guide for the employee application. All endpoint paths below include `/api`.

Read [MOBILE_BRD.md](MOBILE_BRD.md) for what to build and acceptance criteria. Use this file for connection, authentication, attendance, notifications, and shared error handling. Read [MOBILE-REQUESTS.md](MOBILE-REQUESTS.md) when implementing request forms, history, withdrawal, or department manager recommendations; it owns the detailed request contract. Inspect current backend source when a contract changes, and keep both guides consistent.

## 1. Connection and common conventions

- Direct backend development address: `http://127.0.0.1:3002`. Docker Compose exposes it on the development computer at `http://127.0.0.1:4002`.
- Make the base URL configurable by environment. A physical phone's `127.0.0.1` refers to the phone, not the development computer. Use a reachable development server address. The backend defaults to a loopback bind and Compose binds host ports to loopback; LAN access needs explicit host/network configuration. Use HTTPS for the deployed API.
- The mobile app communicates exclusively through REST. Do not connect to the HR database or access backend internal modules.
- Protected requests require `Authorization: Bearer <token>`. Tokens are opaque strings; do not assume JWT format or try to decode an expiry from them.
- JSON requests use `Content-Type: application/json`. Attendance capture uses multipart form data; photo downloads return JPEG bytes.
- POST succeeds with HTTP **201**, including attendance retries that return an existing record. GET/PATCH succeeds with **200**. Do not require every successful endpoint to return 200.
- User, employee, schedule, attendance, and request IDs are UUID strings. Notification IDs are opaque strings and may contain colons; URL-encode path IDs. Use actual IDs returned by the server, not names or national IDs in their place. Example IDs and tokens in this guide are placeholders.
- Date-only fields use real calendar dates in `YYYY-MM-DD` format. Datetimes use ISO 8601 with `Z` or an explicit offset, for example `2026-10-05T08:00:00Z`. Local datetimes without an offset are invalid.
- Request body schemas reject unknown fields. Send only documented fields, using JSON numbers for numeric request fields. Omit optional fields rather than sending null unless explicitly supported.
- Use company/record timezones for display, not the phone timezone. `today` and attendance `workDate` come from the server. Check-in/check-out timestamps are generated by the server.
- Native clients use bearer authentication. The dashboard uses an HttpOnly cookie. Native requests should not add browser Origin or Sec-Fetch headers; if an Origin is sent it must be allowed by server configuration. A browser/Flutter web client needs a separate same-origin proxy or approved browser integration.

All endpoints except health and login require authentication. Attendance and own-request endpoints require an employee-associated account. If `employee` is null in `/auth/me`, disable employee actions; the bootstrap administrator may have no employee profile. Employee identities for submissions are derived from the session: do not submit `employeeId`.

## 3. Sign-in, session, and password

### POST /api/auth/login

```json
{
  "email": "employee@company.example",
  "password": "a-unique-account-password"
}
```

Validation: valid email, maximum 254 characters; email is trimmed and normalized to lowercase. Password is 1-128 characters at login. Preserve password characters; do not trim passwords.

```json
{
  "user": {
    "id": "<user UUID>",
    "name": "Employee Name",
    "email": "employee@company.example",
    "role": "employee",
    "employeeId": "<employee UUID>"
  },
  "token": "<opaque session token>"
}
```

Store the token in platform secure storage and attach it to protected requests, including photo downloads. Do not store it in plain preferences or include credentials/tokens in logs. Sessions expire after 12 hours. There is no refresh-token endpoint. An inactive/deactivated account cannot authenticate; password resets and changes can revoke sessions early.

The server records failed attempts per email. After five failed attempts in a 15-minute window, subsequent attempts during that window return 429. Do not automatically retry login; show the server message. The response does not provide a retry countdown or Retry-After value that the app can rely on.

### GET /api/auth/me

Response shape:

```json
{
  "user": { "id": "<user UUID>", "name": "Employee Name", "email": "employee@company.example", "role": "employee", "employeeId": "<employee UUID>" },
  "employee": {
    "id": "<employee UUID>",
    "employeeNumber": "EMP-000001",
    "nationalId": "00123456789012",
    "name": "Employee Name",
    "email": "employee@company.example",
    "department": "Engineering",
    "jobTitle": "Engineer",
    "startDate": "2026-10-01",
    "scheduleId": "<schedule UUID>",
    "active": true,
    "role": "employee",
    "monthlySalary": null,
    "salaryCurrency": "EGP"
  },
  "company": { "name": "Company name", "timezone": "Africa/Cairo" },
  "today": "2026-10-05"
}
```

`employee` can be null. `monthlySalary` can be null or zero. Keep `nationalId` and `employeeNumber` as strings; national IDs may have leading zeros. Employee profile and salary fields are read-only in the employee app. There is no employee profile update endpoint available to employee accounts.

On launch with a stored token, call `/auth/me` before entering the signed-in app. Network failure is not proof of an invalid session. A protected endpoint's 401 normally means clear the invalid session and show sign-in. Login 401 means invalid credentials. Password-change 401 can mean an incorrect current password: retain the form and validate the session using `/auth/me`; if that also returns 401, clear the session. Do not apply unconditional sign-out to every password-change 401.

### POST /api/auth/logout

Send the bearer token; no JSON fields are needed. On success, remove the stored token and sensitive cached state. If offline, local sign-out can clear the device state but does not revoke the server session; do not report successful server revocation.

### POST /api/auth/password

```json
{ "currentPassword": "old-password", "newPassword": "new-password-2026" }
```

Current password: 1-128 characters. New password: 8-128 characters. Add a matching password confirmation field locally, but do not send it. On success all sessions are revoked, including this one; clear the token and require sign-in again. There are no registration or forgotten-password recovery endpoints; HR/admin creates accounts and resets access.

## 4. Schedules and time handling

`GET /api/schedules` returns an array:

```json
[
  { "id": "<schedule UUID>", "name": "Standard workweek", "start": "10:00", "end": "18:00", "days": [0, 1, 2, 3, 4], "graceMinutes": 15 }
]
```

Find the assigned shift using `employee.scheduleId`. Start/end are `HH:mm` in the company timezone. Weekdays are Sunday=0 through Saturday=6. End earlier than start means an overnight shift. Use returned schedules instead of hardcoding standard or sales hours. Refresh after login and when returning to relevant screens because HR can change assignments.

Attendance records retain their own schedule and timezone snapshots. Display historical records using those snapshots. Overnight `workDate` may be the previous calendar day; use `/attendance/me.workDate` to identify the current workday instead of assuming it equals `/auth/me.today`.

## 5. Attendance: policy, capture, submit, and history

### GET /api/attendance/policy

Current response:

```json
{
  "latitude": 30.023092,
  "longitude": 31.528179,
  "radiusMeters": 50,
  "maxAccuracyMeters": 50,
  "maxCaptureAgeSeconds": 120,
  "maxPhotoBytes": 5242880,
  "photoFormats": ["jpeg", "png"]
}
```

Fetch policy before capture and use returned limits. Radius and accuracy are separate constraints: the measured position must be **at most 50 meters** from the office, and reported GPS accuracy must be positive and at most 50 meters. Accuracy does not increase the allowed radius. Client distance checks help the user; the server makes the final decision.

### GET /api/attendance/me

Returns own employee, current assigned schedule, current `workDate`, and up to 93 latest recorded intervals, ordered by workday descending. This is a record count limit, not a complete 93-day calendar. There is no pagination or date filter on this endpoint and no synthesized absent-day rows.

Attendance record shape (also returned by both attendance POST endpoints):

```json
{
  "id": "<attendance UUID>",
  "employeeId": "<employee UUID>",
  "workDate": "2026-10-05",
  "checkIn": "2026-10-05T07:00:00.000Z",
  "checkOut": null,
  "schedule": { "id": "<schedule UUID>", "name": "Standard workweek", "start": "10:00", "end": "18:00", "days": [0, 1, 2, 3, 4], "graceMinutes": 15 },
  "timezone": "Africa/Cairo"
}
```

Records in `/attendance/me.records` additionally include calculated `status`: `On time`, `Late`, `Not scheduled`, or `Missing check-out`. The POST response has no calculated status; refresh history afterward. Null `checkOut` means open, even when the status says Missing check-out. Lateness is based on the recorded schedule and grace period; an open record becomes Missing check-out when its shift end is reached.

### POST /api/attendance/check-in and POST /api/attendance/:id/check-out

Send exactly these multipart fields for **each** event:

| Field | Format | Validation / app handling |
| --- | --- | --- |
| `latitude` | Numeric text | -90 through 90 |
| `longitude` | Numeric text | -180 through 180 |
| `accuracyMeters` | Numeric text | Greater than 0 and at most policy maximum; use a current position fix |
| `capturedAt` | ISO datetime with offset | At most 120 seconds old; at most 10 seconds in the future compared with server time |
| `photo` | One binary image file | Valid, non-animated JPEG/PNG; nonempty; at most 5 MiB and 20 million pixels |

Do not send `employeeId`, `workDate`, a client check-in/check-out time, or additional fields. Let the HTTP library generate the multipart boundary and Content-Type. Text fields have a 256-byte upload limit. GPS/photo are required for check-out as well as check-in. The server validates decoded image content, not just the file extension, and normalizes accepted photos to JPEG, strips EXIF, and limits dimensions to 1600 pixels per side.

App capture sequence:

1. Load policy and `/attendance/me`; determine the relevant owned open record for check-out.
2. Request camera and precise foreground location permission. Handle denied/permanently denied permission, disabled location services, a location timeout, or inaccurate GPS with an actionable message and retry/settings action.
3. Capture a fresh camera photo and current GPS fix. Convert camera formats such as HEIC to JPEG/PNG when necessary; compress/resize before upload to meet byte and pixel limits. Do not silently substitute an old gallery photo or cached location.
4. Set `capturedAt` to the capture timestamp. If confirmation/upload preparation takes too long, refresh the capture instead of submitting stale evidence. Keep the device clock accurate.
5. Disable duplicate submissions while uploading. Show success only after the API succeeds; then reload attendance.

Server behavior to account for:

- Check-in cannot precede employment. A previous workday left open blocks a new check-in with 409 and requires resolution/HR review.
- One record is stored per employee/workday. Repeating check-in for that workday returns the original record, including if it is already closed; it does not start a second shift.
- Repeating check-out for an already closed owned record returns its original timestamps. Retries still need valid fresh GPS/photo because evidence is validated before the existing record is returned.
- The backend currently allows recording attendance on unscheduled days and labels it Not scheduled; it does not enforce an exact opening/closing time window. Do not assume an unimplemented time-window rule.
- Failed evidence validation leaves attendance unchanged. If a response is lost, first fetch `/attendance/me` to reconcile. Do not blindly queue offline attendance: server timestamps reflect submission, and evidence expires.

### Evidence and private photos

`GET /api/attendance/:id/evidence` returns an array of objects with `event`, `latitude`, `longitude`, `accuracyMeters`, `distanceMeters`, `capturedAt`, `submittedAt`, `policy`, and `photoUrl`. Event is `check-in` or `check-out`. An empty array is valid for historical/HR-entered records.

`photoUrl` is relative to the server origin and already begins `/api/`, for example `/api/attendance/<UUID>/photos/check-in`. Do not prepend `/api` again. Fetch the image with the bearer token; an unauthenticated image widget will fail. Photos are private, `image/jpeg`, and should not be placed in a public cache. Missing photos or another employee's attendance return 404. Historical evidence may show the old 100-meter policy snapshot; the current capture policy is 50 meters.


## 6. Requests and manager workflows

Use [MOBILE-REQUESTS.md](MOBILE-REQUESTS.md) for all request bodies, response fields, limits, status transitions, and manager actions. All eight backend types are supported: `leave`, `holiday`, `sick`, `unpaid`, `urgent`, `mission`, `excuse`, and `forgotten-check-out`.

The employee app lists only own requests and the server-authorized managed queue. Manager recommendations leave the overall request pending; final HR decisions and reopening controls belong to the dashboard. There is no single-request GET, edit, pagination, request-type discovery, or leave-balance endpoint.

## 7. In-app notifications

### GET /api/notifications

Returns HTTP 200:

```json
{
  "items": [
    {
      "id": "<opaque notification ID>",
      "type": "request-decided",
      "title": "Request approved",
      "message": "leave: Coverage arranged (HR Name)",
      "createdAt": "2026-10-06T09:00:00.000Z",
      "readAt": null,
      "requestId": "<request UUID>"
    }
  ],
  "unreadCount": 1
}
```

Fields: `id`, `type`, `title`, `message`, `createdAt`, nullable `readAt`, optional `requestId`/`attendanceId`. Preserve opaque IDs exactly. Display server text as plain text. Do not infer current request status from an old notification title.

| Type | Audience / route |
| --- | --- |
| `request-decided`, `request-reopened`, `manager-reviewed` | Requesting employee; refresh own requests and open matching request |
| `manager-review-required` | Currently assigned department manager; refresh managed queue and open matching request |
| `pending-request`, `missing-check-out` | HR/admin alerts; administration remains outside employee app scope |

The employee event history contains the latest 100 decision/reopening/manager-review events combined. Manager review alerts are live and disappear when resolved or access changes. Ordinary employees do not receive missing-check-out notifications from this service; derive their guidance from `/attendance/me`.

### PATCH /api/notifications/:id/read

Send the bearer token and no body. URL-encode the ID; it is 1–200 characters and not necessarily a UUID. Returns the notification with `readAt`. A repeated read preserves the original timestamp. An unavailable/non-accessible item returns 404; refresh rather than treating that as a session failure. Read state is persisted per user across sign-out/restart.

Flutter behavior:

1. Fetch after sign-in, on foreground return, and after request/attendance mutations. Refresh approximately every 30 seconds while active; stop polling in the background and dispose timers on logout.
2. Show server `unreadCount`, inbox, unread filter, and mark-read actions. Update from the response or refresh after marking read.
3. Resolve request links from `/requests/me` or `/requests/managed`; no `/requests/:id` GET exists. Refresh the relevant list before navigation and handle a removed/inaccessible item.
4. Resolve own attendance links from `/attendance/me`. A record outside its 93-record window cannot be assumed retrievable as full attendance detail; show unavailable guidance.
5. Keep unexpected/unknown notification types readable without exposing privileged actions. HR/admin-linked accounts may return HR alerts; do not route them to employee approval or correction controls.

These are REST/in-app notifications. Background push, WebSockets, email, and SMS are not configured.

## 8. Shared errors and mutation reconciliation

Errors usually contain `{ "statusCode": 403, "message": "...", "error": "Forbidden" }`. `message` may be a string or array; connection/proxy failures may have no JSON. No stable business error codes are provided. Use status and operation context, and show safe readable server messages.

| Outcome | Flutter behavior |
| --- | --- |
| 400 | Show validation/evidence/profile error; preserve editable form input |
| 401 | Require sign-in for invalid protected sessions; handle login/current-password errors as described in section 3 |
| 403 | Show location/role restriction; retain session, refresh permissions where relevant |
| 404 | Explain unavailable/not-owned item and refresh authorized lists |
| 409 | Explain state/overlap/allowance conflict and refresh; avoid blind retry |
| 413 | Reduce upload/attachment size before retry |
| 429 | Explain login lockout; stop automatic attempts; no reliable server countdown is supplied |
| 5xx, timeout, offline | Show a recoverable connection/service error; reconcile uncertain writes before resubmitting |

Disable repeated taps while a write is running. Attendance retries are server-deduplicated but still require fresh valid evidence. Request creation has no idempotency-key contract; never auto-repeat it after timeout. Refresh affected state and let the employee deliberately retry if reconciliation shows no committed change. Apply the same reconciliation approach to withdrawal and manager review; repeated state transitions may return 409.

Do not queue offline attendance: server timestamps reflect submission time and capture evidence expires. Do not show success before a successful response or a confirmed read-back. Distinguish an unavailable API from expired credentials.

## 9. Flutter implementation checklist

- Configure one API origin, such as `http://127.0.0.1:3002`, and append the paths in this guide once. If an existing client instead stores a base ending `/api`, strip that prefix from endpoint paths consistently. Resolve evidence `photoUrl` against the origin.
- Use a shared HTTP client for bearer authorization, JSON/multipart/binary handling, timeouts, safe errors, and cancellation. Scope current-password 401 handling separately from normal session expiry.
- Define separate submission models and response models. Read nullable fields as nullable; tolerate absent historical optional fields. Never serialize a full returned employee/request object into a mutation body.
- Store tokens in platform secure storage; keep passwords out of persistent storage. Clear account-specific memory/files on logout or account switch. Redact credentials, national IDs, location, attachment bytes, and photos from logs/crash reports.
- Use company and saved-record IANA timezone conversion, including daylight saving. Keep request calendar dates as date-only strings rather than accidentally shifting them through UTC.
- Request camera/foreground location access in context and provide denial/settings recovery. Capture both live evidence inputs for each attendance event. Request attachment pickers are a separate workflow.
- Keep private image/document previews in app-private transient storage. Delete temporary captures on success/cancel and clean interrupted-flow files on next launch. Fetch private images with bearer headers, never token query parameters; respect no-store responses.
- Refresh session/profile, attendance, requests, managed queue, and notifications when their screens resume or relevant operations finish. Pause background polling and prevent previous-account responses from populating a new account's state.
- Provide loading, empty, error/retry, and confirmed-success states. Use readable labels and accessible controls; status must not rely only on color.

Production traffic requires HTTPS and normal certificate validation. The phone/emulator must reach the configured backend host; no port, LAN accessibility, or Flutter web proxy should be assumed. Do not choose target platforms, minimum OS versions, or languages silently; these remain BRD decisions.

## 10. Employee scope and verification

Keep employee management, department/manager assignment, global attendance reports/corrections, final HR decisions, reopening, payroll, audit, and schedule/settings mutations in the dashboard. An employee who is a manager receives only the authorized recommendation workflow. A linked HR/admin profile can use personal employee features without turning this app into an administration client.

Before accepting integration, verify the scenarios in [MOBILE_BRD.md](MOBILE_BRD.md), including real-device capture, permission recovery, timezone differences/overnight workdays, lost-response reconciliation, account isolation, and matching REST records in the HR dashboard. Use isolated test accounts/databases. Mock-only tests do not verify backend compatibility; a documentation update does not prove a live-device pilot has passed.
